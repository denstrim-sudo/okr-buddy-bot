# Журнал решений

## Модуль 4 — «Пирамида метрик», Фаза 1 (модель данных и построение)

Дата: 2026-08-07

Назначение: связность OKR разных уровней (Банк ↔ Направления) через метрики.
Основано на идее дерева бизнес-эффектов AI-Native SAFe, но адаптировано.

Решения:

- **Минимальный справочник метрик** (`useMetricsCatalog`, ключ `aimbot.metrics.v1`):
  только `name` + `unit`. Осознанное ограничение — на встрече не заполняют больше
  двух полей. Защита от дублей по нормализованному имени (регистр и пробелы).
- **Связи идут между KR, а не между OKR целиком**, и они many-to-many: один KR
  направления может контрибьютить в несколько банковских KR.
- **Пирамида — самостоятельный слой поверх `useSavedOkrs`** (ключ
  `aimbot.pyramid.v1`): `levels` (okrId → bank|direction), `krMetrics`
  (`okrId:krIndex` → metricId), `contributions` (from/to KR-ссылки). Существующее
  дерево OKR (каскад по горизонтам, one-to-one) не изменено — пирамида только
  читает его данные.
- **Работа на неполной пирамиде**: `findGaps()` (чистая функция в
  `src/lib/pyramid.ts`) показывает разрывы (KR без метрики, KR направления без
  связи вверх, банковский KR без контрибьюторов) как находки для разговора —
  приглушённый warning-стиль, не destructive.
- **Автоподстановка метрики** из поля `kr.metric` сгенерированного OKR при
  привязке; пользователь подтверждает, выбирает из справочника или заводит новую.
- **Оборванные связи** (ссылка на удалённый OKR/KR) игнорируются при чтении, а не
  вызывают ошибку.
- Экспорт/импорт JSON пирамиды с версией схемы — по образцу `useSavedOkrs`.

## Модуль 4 — Фаза 2 (трассировка Решений через метрики)

Дата: 2026-08-07

Решения:

- **Решения не дублируются.** Пирамида читает Модуль 3 из его же хранилища
  (`readModule3Solutions` поверх `aimbot.solutionStudio.v2`); id Решения —
  составной `sliceKey:index`, потому что `S1` не уникален между срезами.
  KR-происхождение восстанавливается сопоставлением текста KR сохранённого OKR —
  оно нужно только для автоподстановки метрики.
- **Связь Решение → метрика many-to-many** (`solutionMetrics` в
  `PyramidState`). Одно Решение реально влияет на несколько метрик; выбирать
  «главную» — потеря информации.
- **Трассировка даёт ОТДЕЛЬНУЮ цепочку на каждую метрику** (`traceSolution`), а не
  «лучшую» ветку. Статусы: `complete`, `broken_at_direction` (с точкой обрыва),
  `orphan_metric`, `no_metrics`. Разрыв — предмет разговора, а не ошибка.
- **AI-проверка связанности** — отдельная edge function `analyze-pyramid-link`
  (три задачи: достройка обрыва, осмысленность связи Решение→метрика,
  соответствие метрики и KR). Грounding проверяется СЕРВЕРНО через общий
  `_shared/textGuards.ts`; негрounded рекомендация не отбрасывается, а
  помечается «не подтверждено цитатой». Выдуманные `target_*` обнуляются
  сверкой с переданным контекстом.
- UI (`SolutionTrace.tsx`) живёт под пирамидой в той же секции и работает на
  неполных данных: показывает статусы, а не пустой экран.

## Решение: пирамида показывает только Решения «в проекте» (2026-08-07)

**Проблема.** Модуль 4 отображал все сгенерированные Решения Модуля 3, включая черновики.

**Решение.** `solutionsForPyramid(studioState)` в `src/lib/pyramid.ts` возвращает id Решений со статусом «в проекте» (`slice.selected` Модуля 3); `SolutionTrace` фильтрует список выбора по нему. Пустое состояние подсказывает отметить Решения как «в проекте» в Модуле 3.

**Ключевое ограничение.** Фильтр применяется ТОЛЬКО на чтение/отображение. Связи `solutionMetrics` в `PyramidState` при снятии статуса не удаляются: пирамида работает с обязательствами, но ручная работа пользователя не теряется — при возврате статуса связи снова доступны.

## Решение: приоритет автоподстановки метрики Решения (Модуль 4)

- Опережающая метрика самого Решения (поле `leading_metric` Модуля 3) предлагается
  ПЕРВОЙ — она точнее описывает механизм Решения, чем более общая метрика
  родительского KR. Метрика KR-происхождения — только запасной вариант, когда
  поле пустое.
- Совпадение со справочником определяется по нормализованному имени
  (`normalizeMetricName`): регистр и лишние пробелы игнорируются.
- Если метрики в справочнике нет — предложение завести одним кликом; справочник
  наполняется из уже сформулированных Решений, без ручного ввода.
- Длинные имена сокращаются до ≤40 символов ЭВРИСТИКОЙ (`shortenMetricName`:
  удаление служебных оборотов «на этапе», «в процессе», «от проведения»,
  «в общем объёме» и длинных слов середины), не LLM — подстановка мгновенная.
  Полный текст сохраняется в `Metric.description`.
- В чипах и кнопках по всему модулю показывается короткое имя, полный текст —
  в `title`. Форма ручного заведения метрики остаётся минимальной (name + unit).
- Пользователь может отредактировать предложенное имя перед созданием или
  отклонить автоподстановку и выбрать метрику вручную.

## Решение: связь МЕТРИКА → МЕТРИКА (Модуль 4)

Опережающая метрика Решения редко стоит прямо в KR. Раньше такая метрика помечалась как «ни к чему не привязана» и трассировка обрывалась. Добавлен нижний ярус пирамиды: связь метрика → метрика (many-to-many) — утверждение «сдвиг А приведёт к сдвигу Б».

- `PyramidState.metricInfluences: {from,to}[]`, циклы запрещены (`detectMetricCycle`), само-связь запрещена.
- `traceSolution` идёт BFS по графу влияний до первой метрики, стоящей в KR; промежуточные метрики видны в `path` как шаги `kind: "metric"`, KR-шаги — `kind: "kr"` (`isKrStep`).
- UI: у оборванной цепочки кнопка «Связать с метрикой выше»; в списке кандидатов метрики, уже стоящие в KR, идут первыми.
- Аудитор `analyze-pyramid-link` получает только связи метрик из цепочек данного Решения и может вернуть тип `metric_influence_weak` (натянутая причинность) с обязательной цитатой и валидируемыми `target_from_metric_id` / `target_to_metric_id`.
- Экспорт документа включает промежуточные метрики и участвующие связи влияния.
