## Диагноз

**«Видно только 2 модели»** — это клиентский фоллбек `FALLBACK_CATALOG` из `src/contexts/ModelContext.tsx`. Бэкенд `list-ai-models` сейчас работает и отдаёт все 20 моделей (проверил прямым вызовом). Значит при загрузке страницы вызов `supabase.functions.invoke("list-ai-models")` упал/таймнулся (вероятно — холодный старт edge-функции + загрузка `corsHeaders` с `esm.sh` под нагрузкой). После фоллбека повторных попыток нет — список так и остаётся из 2 строк до перезагрузки.

**«Ошибка edge function» в модуле 1** — текущий тост в `OkrGenerator` показывает generic-сообщение и не доносит реальный `data.error` из ответа функции (`AI-провайдер вернул ошибку…`, `Модель X недоступна`, `timeout`, и т.п.). Из-за этого нельзя понять, что именно произошло: упала ли модель, истёк ли таймаут или нет ключа.

## Что меняем (TDD, по проектным правилам)

### Фаза A. Стабилизировать каталог моделей

1. **Убрать зависимость от esm.sh** на горячем пути.
   - `supabase/functions/list-ai-models/index.ts` и `supabase/functions/_shared/ai.ts`: заменить `import { corsHeaders } from "https://esm.sh/@supabase/supabase-js@2.105.1/cors"` на локальную константу:
     ```ts
     export const corsHeaders = {
       "Access-Control-Allow-Origin": "*",
       "Access-Control-Allow-Headers": "authorization, x-client-info, apikey, content-type, x-retry-count",
     };
     ```
   - Один внешний CDN-импорт меньше → быстрее cold start, нет риска 503 от esm.sh.

2. **Сделать клиент устойчивым к одной осечке.** В `src/contexts/ModelContext.tsx`:
   - В `fetchModelCatalog` добавить один retry с задержкой 1200 мс, если первый вызов вернул `degraded:true` или попал в `catch`.
   - Существующий контракт (`{ models, degraded }`) и тесты сохраняем; добавляем новый кейс в `src/contexts/__tests__/ModelContext.test.tsx`: «первый invoke падает → второй успешен → возвращает полный каталог, не FALLBACK».

3. **Дать пользователю ручное восстановление.** В `src/components/aimbot/ModelSelector.tsx`:
   - Кнопка-иконка «Обновить список» рядом с селектом, дергает `refresh()`, который нужно экспонировать из `ModelContext` (`refresh: () => Promise<void>`).
   - Тест в `ModelSelector.test.tsx`: клик по кнопке вызывает `refresh` из контекста.

### Фаза B. Показать настоящую причину ошибки в модуле 1

4. **Прокидывать `data.error` наружу.** В `src/components/aimbot/OkrGenerator.tsx` (и идентично в обработчиках вызовов `interpret-okr-input` / `draft-okr` / `validate-okr` внутри генератора):
   - После `supabase.functions.invoke(...)` проверять не только `error`, но и `data?.error`. Если он есть — `toast.error(data.error)` вместо generic-строки.
   - Если ответ содержит `_meta.fallback_reason` с `model_unavailable` — мягкий `toast.warning` через уже существующий `notifyModelFallback` (вызов уже есть в части мест — добавить туда, где забыт).
   - Тест в `OkrGenerator.test.tsx`: мок invoke возвращает `{ data: { error: "Модель X недоступна" }, error: null }` → отображается ровно эта строка.

## Журнал решений

### 2025-07-02 Фиксация канонического набора правил аудита
- **Контекст/проблема:** модель изобретала правила вне свода (например, "CONTEXT_1"), severity одного правила плавала между прогонами → нестабильный score.
- **Решение:** `buildParameters(horizon)` с жёстким enum id и `minItems === maxItems`; `severityFor(id, horizon)` серверно переопределяет severity до recompute.
- **Отвергнутые альтернативы:** —
- **Статус:** реализовано.

### 2025-07-02 Обоснование фейлов цитатой (isGrounded)
- **Контекст/проблема:** критические фейлы без указания, что конкретно не так (например, "нет исхода" на KR с явным исходом).
- **Решение:** `isGrounded` требует дословную цитату из текста OKR для `pass=false`; не переопределяет вердикт, только помечает "не подтверждено цитатой".
- **Отвергнутые альтернативы:** —
- **Ограничение:** для set-fail правил (KR10 — отсутствие leading) цитата структурно невозможна — это известный компромисс.
- **Статус:** реализовано.

### 2025-07-02 Горизонт-специфичные few-shot эталоны
- **Контекст/проблема:** поверхностные вердикты — модель сравнивала с абстрактным определением правила, а не с образцом.
- **Решение:** `getFewShotBlock(horizon)` — 3 симметричных набора (KR3, KR10) для strategic/block/quarter, отличие только в горизонте замера.
- **Отвергнутые альтернативы:** единый набор примеров всех уровней — путал слабые модели.
- **Статус:** реализовано.

### 2025-07-02 Логика достижимости target по горизонту
- **Контекст/проблема:** —
- **Решение:** target реалистичен, если прогресс виден на уровень детализации вниз (стратегия→полугодие/квартал; год→квартал; квартал→спринт/месяц).
- **Отвергнутые альтернативы:** произвольные целевые проценты — учат недостижимым обещаниям.
- **Статус:** реализовано (зашито в эталоны).

### 2025-07-02 Chain-of-thought reasoning до вердикта
- **Контекст/проблема:** —
- **Решение:** поле `reasoning` в схеме ПЕРЕД `pass`, модель рассуждает до вывода.
- **Отвергнутые альтернативы:** ограничение длины reasoning — решили НЕ ограничивать, наблюдать на прогонах, где слабые модели (deepseek/llama) льют воду, и ограничивать прицельно.
- **Статус:** реализовано, лимит на наблюдении.

### 2025-07-02 Разделение аудитор/редактор (рычаг 2)
- **Контекст/проблема:** —
- **Решение:** аудит и переписывание OKR — два раздельных вызова, чтобы редактор не создавал новых нарушений, исправляя одно.
- **Отвергнутые альтернативы:** —
- **Статус:** отложено — риск задеть существующие retry/sanitize/suspicious, делать отдельным заходом.

### 2026-07-02 Разделение аудитор/редактор (рычаг 2, реализовано)
- **Контекст/проблема:** аудитор одновременно выносил вердикт и переписывал OKR — переписывание тянуло к новым нарушениям (напр. цифры в rewritten_objective), а стоимость каждого аудита была завышенной.
- **Решение:** `validate-okr` принимает `mode`. `mode=audit` (дефолт) — только вердикты по правилам, БЕЗ rewritten_*, все существующие механизмы (severity-override, recompute, isGrounded, retry-suspicious) сохранены. `mode=fix` — отдельный вызов РЕДАКТОРА (buildEditorPrompt + buildEditorParameters) с явной инструкцией «закрой ВСЕ проваленные правила разом, не создавая новых»; sanitizeRewrittenObjective работает и здесь.
- **UI:** после аудита при наличии `pass=false` появляется кнопка «Предложить исправления» — второй вызов идёт только по клику.
- **Отвергнутые альтернативы:** оставить один вызов с двумя ролями (высокая температура смешивания задач); разбить на два ЭФ (лишняя сущность, тот же контракт).
- **Статус:** реализовано.

### 2026-07-02 Сохранение исправленной версии OKR = replace по id
- **Контекст/проблема:** после аудита улучшенный OKR приходилось «сохранить как новый», из-за чего плодились дубли, а связи parent→child терялись.
- **Решение:** `useSavedOkrs.replace(id, objective, plan)` обновляет запись НА МЕСТЕ: `id`, `savedAt`, `parentOkrId`, `parentKrIndex` сохраняются, дети продолжают ссылаться на тот же id; добавлено поле `updatedAt`. В `OkrValidator`:
  - если пришёл `sourceOkrId` (OKR открыт из дерева) — кнопка «Сохранить исправленную версию» вызывает `replace`;
  - иначе — «Сохранить как новый» с `ParentKrPicker` для выбора родителя.
- **Отвергнутые альтернативы:** создавать новую запись + помечать старую как «archived» (усложняет дерево, требует UI-скрытия архивных); хранить историю версий (следующее большое решение — вместе с базой).
- **Статус:** реализовано.

### 2026-07-03 Коуч-режим редактора OKR (mode=fix)
- **Контекст/проблема:** повторный аудит после «Предложить исправления» деградировал: редактор чинил каждое правило изолированно, ломал читаемость, вставлял правдоподобные, но выдуманные числа, и дублировал смысл между KR (например, новый KR2 повторял KR1).
- **Решение (вариант 2 — сохранение ядра):** переписан `buildEditorPrompt` в «коуч-режим». Пять принципов, зашитых в системный промпт:
  1. МИНИМАЛЬНОСТЬ — меняем только то, что нарушает правило.
  2. СОХРАНЕНИЕ СМЫСЛОВОГО ЯДРА — метрика/объект/тема исходного KR не подменяются.
  3. ЧЕСТНОСТЬ С ДАННЫМИ — вместо выдуманных чисел обязательный плейсхолдер `X/Y` (в т.ч. `X%/Y%`), в `editor_note` пояснение, откуда взять реальные значения.
  4. ОБЗОР НАБОРА — редактор видит ВЕСЬ набор KR (не только failed) и молча избегает дублей между KR.
  5. ОПОРА НА ЭТАЛОНЫ — сверка с `getFewShotBlock(horizon)` без дословного копирования.
- **Схема ответа:** в `buildEditorParameters` добавлено опциональное поле `editor_note` (1-2 предложения о том, что изменено/сохранено и откуда взять X/Y). `rewritten_*` остались required. `ValidationReport.editor_note?: string` — на клиенте.
- **UI (`OkrValidator`):** `editor_note` рендерится под блоком AI-предложений с префиксом «Коуч:». Плейсхолдеры `X/Y` (и `X%/Y%`) визуально подсвечиваются через `<mark data-testid="placeholder-xy">` (жёлтый чип), чтобы на встрече было сразу видно: тут нужно вписать реальное число. Регэксп ловит только целые слова — `XML/YAML` не триггерятся.
- **Что НЕ трогали:** механизмы `mode=audit` (severity-override, `applyScoreRecompute`, `isGrounded`, `isAuditSuspicious` + retry) — без изменений; `sanitizeRewrittenObjective` продолжает применяться к ответу редактора.
- **Отвергнутые альтернативы:** режимы «хирург/консультант» (два пресета интенсивности вмешательства) — отложены до появления явной пользовательской потребности; ужесточение промпта до полного запрета цифр в KR — отклонено, цифры-плейсхолдеры X/Y нужны, а реальные baseline/target в KR разрешены.
- **Статус:** реализовано.
