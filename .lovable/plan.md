# Почему падает вызов edge function на «не-GPT-4o» моделях

## Что проверено (реальные вызовы функций)

| Функция | Модель | Результат |
|---|---|---|
| `interpret-okr-input` (лёгкая схема) | `claude-haiku-4.5` | 200, ~7 c, корректный JSON |
| `interpret-okr-input` | `gemini-2.5-pro` | 200, ~10 c, корректный JSON |
| `validate-okr` (тяжёлая схема) | `gpt-4o` | 200, полный отчёт |
| `validate-okr` | `gemini-2.5-pro` | ответа нет, запрос оборван по времени |
| `validate-okr` | `claude-haiku-4.5` | ответа нет, запрос оборван по времени |

Вывод: дело **не** в самих моделях и не в каталоге — Claude и Gemini работают. Ломается конкретно **тяжёлый вызов аудита** (`validate-okr`, а по той же схеме и `generate-solutions`/`validate-solution`) на всех моделях, кроме `gpt-4o`. В логах edge-функций ошибок нет: функция не возвращает ошибку, она висит до обрыва соединения — в браузере это и есть «ошибка вызова edge function».

## Причина

1. Схема аудита стала очень тяжёлой: для каждого правила требуется `reasoning`, `evidence`, `grounded`, `severity`, `why`, плюс блок `kr_perspectives` и целиком переписанный OKR. У не-OpenAI моделей (через OpenAI-совместимый шлюз AIAI.BY) генерация такого tool-call идёт в разы дольше, чем у `gpt-4o`.
2. В `supabase/functions/_shared/ai.ts` таймаут одной попытки — 90 секунд, а попыток до трёх (основная → retry → fallback). Итого до ~270 секунд. Соединение с браузером рвётся раньше, чем функция успеет ответить хоть чем-то.
3. Fallback на `gpt-4o` срабатывает только по кодам `model_unavailable`, `provider_unavailable`, `timeout`, `network_error`. Но при «просто медленно» первая попытка ждёт все 90 с, и только потом начинается вторая — бюджета уже нет.
4. Нет общего дедлайна на запрос — только на отдельную попытку.

## Что делаем

1. **Общий дедлайн запроса.** Ввести бюджет ~55 секунд на весь `runWithFallback`: до 25 с на выбранную пользователем модель, оставшееся время — на `gpt-4o`. Функция всегда отвечает раньше, чем оборвётся соединение.
2. **Быстрый fallback на GPT-4o.** Если выбранная модель не уложилась в свои 25 с или вернула `no_tool_call` / `invalid_json` / `aiai_error`, сразу уходим на `gpt-4o` и отдаём результат с пометкой `_meta.fallback_reason` — пользователь видит тост «модель X не успела, выполнено через GPT-4o», а не ошибку.
3. **Убрать лишний retry в ту же модель.** Порядок: выбранная модель → `gpt-4o` → один retry `gpt-4o` только если остался бюджет.
4. **Понятная ошибка вместо обрыва.** Если бюджет исчерпан полностью — 504 с русским текстом и `_meta`, чтобы UI показал сообщение.
5. **Облегчить тяжёлую схему для не-OpenAI моделей.** В `validate-okr` при модели, отличной от `gpt-4o`, не требовать `reasoning` для каждого правила (оставить только итоговый разбор) — это главный источник времени генерации. Для `gpt-4o` поведение не меняется.
6. **Клиент.** В `OkrGenerator`, `OkrValidator`, `useSolutionStudio` показывать текст ошибки из тела ответа; сетевой обрыв подписывать как «превышено время ожидания, попробуйте GPT-4o».

## Технические детали

- `supabase/functions/_shared/ai.ts`: сделать таймаут параметром попытки, добавить `deadlineAt` в `runWithFallback`, расширить `shouldFallbackToDefault`, убрать безусловный retry в исходную модель.
- `supabase/functions/validate-okr/index.ts`: `buildParameters(horizon)` получает флаг «облегчённая схема» (без обязательного `reasoning` в каждом правиле) для не-`gpt-4o` моделей.
- Тесты Deno (`_shared/ai.test.ts`, `validate-okr/index.test.ts`): fallback по `no_tool_call`; отсутствие второй попытки в ту же модель; выход по дедлайну с 504 и корректным `_meta`; облегчённая схема для не-`gpt-4o`.
- Фронтенд: общий хелпер разбора ошибки `functions.invoke` вместо дублирования в трёх местах.
- Каталог моделей и `list-ai-models` не трогаем — они работают штатно.
