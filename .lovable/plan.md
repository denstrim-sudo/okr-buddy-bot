
## Проблема

В превью каталог моделей приходит полный (~20 шт.), в опубликованном приложении иногда падает до «каталог временно недоступен» + 2 модели в списке.

Причина не в билде и не в CORS: бандл на `denstrim.by` корректно бьёт в ту же edge-функцию `list-ai-models`. Разница — во времени вызова: если в момент открытия апстрим `vedai.by/api/v1/models` отвечает ошибкой или таймаутом (15 c), функция возвращает `FALLBACK_LIST` (2 модели, `degraded:true`). При этом:

- на сервере кэш пишется только при успехе → после неудачи следующий вызов снова идёт в апстрим и снова может упасть;
- на клиенте каталог живёт только в памяти → каждый новый вход в приложение начинает с пустого состояния и полностью зависит от одного удачного ответа;
- клиентский `fetchModelCatalog` делает всего 2 попытки с паузой 1.2 c — этого мало на «холодный» апстрим.

## Что делаем

Две небольшие правки, только слой каталога моделей. Никакой бизнес-логики генератора/аудита не трогаем.

### 1. Edge `supabase/functions/list-ai-models/index.ts` — Last-Known-Good кэш

- Разделить TTL: `FRESH_TTL = 10 мин` (как сейчас — свежий ответ, `cached:false/true` не важно), `STALE_TTL = 24 ч` (используем при недоступности апстрима).
- При успехе — писать в кэш `{ at, models, degraded:false }` как раньше.
- При неудаче апстрима:
  - если есть кэш моложе `STALE_TTL` — отдавать его с `degraded:true, cached:true, stale:true` (сейчас условие `if (cache)` уже почти это делает, но нет ограничения по возрасту и нет отметки `stale`);
  - если кэша нет вообще — отдавать текущий `FALLBACK_LIST` + `degraded:true`.
- Не менять состав `CURATED` и порядок; не расширять `FALLBACK_LIST` — курированный набор идёт только через успешный ответ апстрима (пересечение с живым каталогом), это остаётся инвариантом.
- Обновить `index.test.ts`: добавить сценарии «апстрим упал, кэш свежий → отдаём кэш `stale:true`», «кэш просрочен по `STALE_TTL` → отдаём `FALLBACK_LIST`». Существующие тесты оставить.

### 2. Клиент `src/contexts/ModelContext.tsx` — локальный LKG-кэш и переиспользование при старте

- Добавить второй ключ localStorage, например `aimbot.aiModelCatalog.v1`, где храним `{ at:number, models:AiModelEntry[] }` после каждого успешного (не `degraded`) ответа.
- При инициализации `ModelProvider`: сразу подставлять сохранённый каталог, если он есть и не старее ~7 дней. Это убирает мигание «2 модели» на первом рендере и переживает падение апстрима на старте.
- В `fetchModelCatalog` увеличить количество повторов с 2 до 3 и добавить экспоненциальную паузу (1.2 c → 3 c). Никакой смены семантики: если все попытки degraded — возвращаем последнюю.
- `loadCatalog(manual)`: если новый ответ `degraded` и в памяти уже есть полный каталог из LKG, оставляем его в UI, а тост показываем только при `manual` рефреше — сейчас поведение почти такое, но без LKG первый автозагруз перезапишет полный список на fallback.
- Тосты не менять по смыслу. Добавить только более мягкий текст, если ответ `stale:true` («каталог показан из кэша — провайдер временно недоступен»).

### Тесты

- `src/contexts/__tests__/ModelContext.test.tsx`: добавить кейсы «на старте берём LKG из localStorage», «degraded-ответ не затирает LKG-каталог», «после успешного ответа LKG обновляется».
- `supabase/functions/list-ai-models/index.test.ts`: сценарии `STALE_TTL`, описанные выше.
- Ничего в UI-компонентах (`ModelSelector`, `AppHeader`) менять не нужно — контракт `useAiModel()` остаётся прежним.

### Что НЕ делаем сейчас

- Не расширяем `FALLBACK_LIST` до полного `CURATED` (это скрыло бы реальные падения апстрима и могло бы показать пользователю модели, которых у провайдера сейчас нет).
- Не добавляем ретрай/фолбэк на другой апстрим — это отдельная задача уровня инфраструктуры.
- Не меняем логику вызова моделей в `_shared/ai.ts`.
